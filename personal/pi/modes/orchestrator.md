## Brain bookkeeping (main session)

- **Ensure a project exists before dispatching project work.** Find first: use `brain-project-find` across all tracked banks. If nothing matches, create one with `brain-project-create` in the correct bank — pick by repo/team ownership, fall back to the personal bank, and ask the user when the bank is ambiguous. Honour an explicit user opt-out and proceed without a project. Threshold: work producing a diff, report, or PR = project work; single-question asks are not.
- **Resolve the project path once, then thread it down.** Every subagent brief carries absolute artifact paths (plans → `<project>/local/plans/<date>-<slug>.md`, research/scout reports → `<project>/local/reports/…`, review reports → `<project>/local/reviews/…`, verification summaries → `<project>/local/reports/…`) plus the lineage chain so far. Parent resolves, worker writes — subagents never run brain commands. Sub-orchestrators inherit the threading duty from the global orchestrator agent (`~/.pi/agent/agents/orchestrator.md`), so the chain carries it below you. Promotion to `documents/` happens later via the brain-project-document flow, never by a worker.
- **Keep `activeProjects.md` in sync** (personal bank `core/`): every open or draft PR gets one line; remove or merge-mark the line when the PR closes. Every PR gets a project in the correct bank unless the user opts out.
- **Append lineage to `<project>/local/sessions.log`** — top-level orchestrator only, one line per session: `[date] [root: <sessionId>] -> [role: <sessionId>] -> … | <optional one-line note>`. Sub-orchestrators never write it; they return their children's hops in their final reports so the root can append complete chains.
- **Attribute bank-work spawns with project args.** Each doc-update pass spawns ONE `brain-orchestrator` with its task-package args: `projects[]` of `{bank, bankPath, projectPath, artifacts[], summary?, supersededDecisions[]?}` (`bankPath` = absolute bank checkout root, `projectPath` bank-relative; resolve once, e.g. `brain project path <bank> <type> <name>`) plus `lineage` and `parentSummary` — never omit args; the extension's argsSchema refusal enforces this. Put every project of the pass in one package. The drafters read the project docs themselves; do not duplicate project context in the brief beyond what the task needs.
- **Review the pass when it reports done.** brain-drafters edit project files directly in per-project worktrees; brain-orchestrator integrates them serially into the bank checkout and reports per-project diffs, commits, and conflicts. When its report lands, review the integrated diff against the bank's documentation rules (word budgets, append-only sections) and record the report — never re-apply or re-narrate entries. Dispatch passes as work completes, never batched to session end — long sessions lose the middle. Nothing is pushed: the pre-submit autosquash (`git rebase -i --autosquash @{upstream}`, folding each project's `fixup!` commits into its scaffold commit) and `brain submit` remain the user's — remind, never run.
- **Update core files as work completes, not just at session end.** After each task — or each group of dependent tasks — completes: append to `dailyContext.md` (Completed / Key Decisions sections, one line per entry, never overwrite) and sync `activeProjects.md` if a project/PR status changed. Don't batch a whole session's completions into one end-of-day write; record them as they land so a crash loses nothing.
- **Never serialize orthogonal work.** Before queuing new work "for the next batch" behind an in-flight worker, ask what actually couples them. The hard constraint is one writer per worktree/branch — not one writer at a time. Orthogonal changes get their own worktree and run immediately, in parallel, at every repo (extension, world, brain). Serializing uncoupled work is a habit, not a safety property; default to parallel and check coupling only when the changes touch the same files or regions.
- **High-importance things go in the user's Inbox (`escalate`), never chat prose.** Decisions the user must make, infrastructure issues causing churn or disruption, next-steps questions, blocked-on-user items (escalate the blocked task id), and stream outcomes (escalate the stream id) — all through `escalate`, resolved with `ack_inbox_item` once the user acknowledges them in conversation. Outcome rows persist until acked; never let a finished stream's result vanish into chat scroll.

## Gate presentation (helix)

- **Open the files before summarizing.** When a helix gate message references artifact files (`checkpoints.md`, `test-cases.md`, `gates.md`, `ui-review` runs, diffs), open each referenced file in the user's nvim pane BEFORE presenting the gate summary (per command conventions: reuse an existing nvim pane via tmux send-keys `:e <path>`, else `tmux split-window -h -p 70`). The developer reviews files, not summaries.
